Extra Documentation and Design Notes

Graph Representation and Parsing

Data model

The implementation separates the problem into four layers:

  • ProgramPoint: one program line plus an optional + / - marker.
  • LiveRange: one input line from the ranges file.
  • Web: a merged set of live ranges for the same variable.
  • Graph<int>: the interference graph, where each vertex stores a web id.

The provided graph structure from the course was preserved as the primary graph representation. The only conceptual adaptation is that vertex labels are int web identifiers instead of domain objects. This keeps the graph reusable and lets the allocation algorithms work with a compact vertex set.

Web construction

The input file may contain multiple live ranges for the same variable. Those ranges are merged into a web whenever they share at least one program point. The implementation uses a union-find structure over the live ranges of a single variable:

  • Build one union-find element per live range.
  • For every pair of ranges of the same variable, test whether they overlap.
  • Union overlapping pairs.
  • Emit one web per connected component.

Two implementation details matter for correctness and testing:

  • The emitted webs are sorted deterministically by variable name and first live line.
  • The final web ids are reassigned after sorting so output files are stable.

Interference rule

Two webs interfere if they are simultaneously live at some program point. The implementation handles the register-reuse exception for adjacent live ranges:

  • if one web ends on line L due to a last use (-) and another web starts on the same line L due to a definition (+), they do not interfere.

This rule is implemented explicitly in InterferenceGraph::interferes.

Aggregated web output

The output format uses one line per web, not one line per constituent live range. Internally, this means:

  • collect all program points from all ranges of the web;
  • sort them by line number;
  • collapse duplicate line numbers;
  • if the same line contains both + and -, treat it as an internal merge point and print it without a marker.

This preserves the intended fused-web representation: each final web has one stable id and one sorted program-point list.

For the alternative algorithms, the writer appends a small processing-friendly metadata section after the assignment section. The base format remains unchanged, and tools can parse the extra records line-by-line:

  • spilling/free records: spills: N, followed by spill: webX;
  • splitting records: splits: N, followed by split: webX -> webY,webZ.

The split record names the source web selected by the heuristic and the two derived web ids present in the final web list. The implementation reuses the source id for the left derived web and allocates a new id to the right derived web, making the mapping deterministic and easy to inspect.

In addition to the text output, the application can export a colored DOT graph for the final allocation. Register-assigned webs are filled with register colors, memory-assigned webs are gray boxes, and split-derived webs have a highlighted border. Batch mode writes this graph automatically next to the allocation file using the same base name and a .dot extension.

Complexity

Step Complexity
Parse ranges O(L * P)
Parse config O(L)
Build webs O(V * R^2 * P log P)
Build interference graph O(W^2 * P + E * W)

The bounds above describe the current implementation. The extra log P in web construction comes from set-based overlap tests, and the E * W graph-building term comes from the vector-backed course graph, where endpoint lookup is linear in the number of webs.

T2.1 - Basic Register Allocation

Approach

The basic allocator uses a simplify/select structure:

  • Maintain the set of active vertices.
  • Repeatedly remove every active vertex with degree < K and push it onto a stack.
  • If no such vertex exists, pick a spill candidate heuristically and remove it.
  • Pop the stack and greedily assign the first available register.

In the basic mode, any spill means the allocation is considered infeasible. The service layer then converts the result into the specification-compliant fallback output:

  • registers: 0
  • every web mapped to M

Complexity

Step Complexity
Simplification + select O(W * (W^2 + E))

The W^2 component comes from repeated findVertex calls on the provided vector-backed graph. With an indexed graph representation, this would reduce to the usual simplify/select adjacency-scan cost.

T2.2 - Register Allocation with Spilling

Approach

For the spilling mode, spilling is no longer treated as a failure. The algorithm:

  • tries to color the graph with zero forced spills;
  • if that fails, forces one spill and retries;
  • continues until either a valid coloring is found or the configured bound K is exhausted.

The spill heuristic is deterministic and pressure-oriented:

  • prefer the currently highest-degree web;
  • break ties by lower web id to keep results deterministic.

When a valid coloring is found, only the selected spilled webs are mapped to memory. Unlike the basic mode, the result remains feasible.

The output metadata records the exact web ids selected by this heuristic, for example spills: 1 followed by spill: web0.

T2.3 - Register Allocation with Splitting

Approach

Web splitting is used when the user explicitly selects splitting, K. The implementation keeps the problem local and deterministic:

  • first, try to color the current graph with no splitting;
  • if that fails, pick one of the currently uncolorable/high-degree webs;
  • split it into two derived webs;
  • rebuild the interference graph;
  • retry coloring;
  • stop after at most K successful split operations.

Two split strategies are used:

  • if the original web already contains multiple ranges, split those ranges into two ordered groups;
  • if it contains only one range, split the sequence of program points into two contiguous derived ranges and normalize their endpoints with + and -.

This approach is deterministic and directly targets the source of excessive interference by slicing a long-lived web into shorter derived webs.

The output metadata records every performed split as split: webSource -> webLeft,webRight, which identifies the selected source web and the derived webs that define the save/restore boundaries.

T2.4 - Custom Allocation Strategy

Approach

The custom mode uses pressure-aware greedy coloring:

  • for each uncolored web, count how many distinct register colors already appear in its colored neighbors;
  • select the web with the highest such count, because it has the fewest safe choices left;
  • break ties using the highest graph degree, because that web has more total interference constraints;
  • assign the lowest-numbered compatible register;
  • if every register is blocked by a colored neighbor, assign the web to memory.

The rationale is to spend registers first on the webs under the strongest current pressure. Less constrained webs are delayed because they still have more available choices. This keeps the invariant that no two interfering colored webs share a register, while still producing a feasible partial allocation by using memory only for webs that cannot be colored safely.

Complexity

Step Complexity
Pressure-aware selection and coloring O(W * (W^2 + E))

Each selection round scans the remaining vertices and their adjacency lists, and each vertex lookup is linear in W in the current graph structure.

Error Handling, CLI, and Testing

CLI

The application supports:

  • an interactive menu (./register_alloc);
  • the batch interface: ./register_alloc -b ranges.txt config.txt allocation.txt

Batch mode now returns a non-zero exit code when one of the input files cannot be parsed, which makes the test script dependable.

Testing

The test suite has three goals:

  • verify parsing and output formatting corner cases;
  • pin down the interference and web-fusion semantics;
  • validate the behaviour of all four allocation modes.

The integration tests use the six baseline datasets plus dedicated spilling, splitting, and free scenarios.
